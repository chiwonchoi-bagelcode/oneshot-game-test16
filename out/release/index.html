펭귄 슬라이드 (Penguin Slide) — 기획서

이 문서는 반복할 때마다 고치는 살아 있는 문서입니다. 맨 아래 변경 이력에 무엇을 왜 바꿨는지, 시도했다가 버린 아이디어를 남깁니다.

1. 한 줄 소개

날지 못하던 꼬마 펭귄이 눈 언덕을 배로 미끄러지고 하늘로 튀어 올라, 뒤쫓는 눈보라보다 멀리 — 언젠가 하늘 끝 섬까지 날아가는 원터치 세로형 게임.

2. 누가, 언제, 왜 재미를 느끼나

누가어떤 순간왜
짧은 틈에 폰을 켜는 캐주얼 플레이어내리막에서 꾹 눌렀다가 골짜기 바닥에서 손을 떼는 순간, 펭귄이 "휙" 솟구칠 때내 타이밍이 그대로 속도와 높이로 돌아온다. 규칙은 하나지만 언덕 모양이 매번 달라 "지금!"을 다시 찾아야 한다
같은 사람, 몇 판 뒤강화 후 같은 언덕을 지난 판 궤적(유령선)보다 확연히 높이 넘을 때성장이 눈에 보인다. "한 판만 더"
기록을 노리는 사람눈보라가 등 뒤에 바짝 붙었다가 리듬을 되찾아 떼어낼 때아슬아슬함과 안도
오늘 그만둔 사람다음 날 마을에 들어가 알이 부화해 있고, 건조대에 물고기가 쌓여 있을 때내가 없는 사이에도 마을이 살아 있다

3. 참고 게임 — 배운 것 / 다르게 한 것

참고배운 것다르게 한 것
Tiny Wings누르면 무거워지고(내리막 가속) 떼면 가벼워지는(오르막 도약) 원터치 물리, 완벽 착지 연쇄 → 피버가로 → 세로 화면. 세로 공간을 "솟구침"의 무대로 쓰고, 높이 날수록 카메라가 물러나 지나온 언덕과 다음 섬이 한눈에 보이게 함. 해가 지는 대신 얼굴 있는 눈보라가 쫓아옴
Ski Safari등 뒤에서 다가오는 눈사태의 압박, 화면 왼쪽 끝의 위협잡혀도 벌이 아니라 "오늘은 여기까지". 눈보라 정령이 펭귄을 눈덩이로 굴려 보내는 귀여운 마무리. 거리·물고기는 모두 남음. 리듬이 좋으면 눈보라가 화면 밖으로 밀려나되 너무 멀어지지 않게(고무줄) 해 긴장을 유지
Learn to Fly판 사이 업그레이드로 "매번 조금 더 멀리". 첫 판 직후 첫 강화강화가 실력을 대신하지 않도록 도약 강화는 이륙 속도에 비례(타이밍이 나쁘면 효과도 작음). 강해질수록 더 높은 물고기 길·바람길을 노릴 수 있고, 높이 날수록 착지가 어려워지는 위험이 커짐
마을 키우기류판 밖에서 눈에 보이게 커지는 공간 = 재방문 이유마을이 그냥 장식이 아니라 코어에 돌아옴: 마을 펭귄 수만큼 물고기 보너스, 등대가 출발 섬 선택을 열어 줌, 건조대는 쉬는 동안 물고기를 모음

4. 조작

  • 화면 아무 곳이나 누르고 있기 → 펭귄이 배를 깔고 무거워져 내리막에서 빠르게 미끄러짐 / 공중에서는 빠르게 내려옴(다이브).
  • 손 떼기 → 가벼워져 오르막을 타고 하늘로 날아오름.
  • 그 외 조작 없음. 세로 화면, 한 손 엄지로 화면 아래쪽 어디를 눌러도 됨. 펭귄과 지면은 화면 중상단에 있어 손가락이 가리지 않음.

손맛 규칙 (물리)

  • 내리막에서 누름 → 경사 방향 가속이 커짐(무거워짐).
  • 오르막에서 누름 → 감속(벌). 그래서 "골짜기 바닥에서 떼기"가 정답 리듬.
  • 떼고 있으면 언덕 꼭대기 곡률에서 원심력이 중력을 이기는 순간 자연스럽게 이륙. 빠를수록 가파른 각도에서 떠서 높이 솟음.
  • 완벽 착지: 내리막 경사와 비행 방향이 거의 일치하게 내려앉으면 가속 + 반짝임. 3연속이면 눈꽃 질주(피버). 언덕 꼭대기를 살짝 스치는 짧은 뜀(0.35초 미만 또는 11m 미만)은 비행으로 치지 않아 판정·연속에 영향 없음.
  • 쿵 착지: 오르막에 처박으면 속도를 잃고 어지러운 별. 이해 가능한 실패.

5. 한 판의 흐름 (목표 30초 ~ 3분)

  1. 출발: 펭귄이 첫 언덕 꼭대기에서 출발. 첫 판에는 손가락 안내만 나오고 글은 최소.
  2. 리듬 타기: 언덕마다 누르고-떼기. 물고기는 낮은 길(안전, 적음)과 높은 길(위험, 많음, 황금 물고기)에 배치.
  3. 눈보라: 화면 왼쪽 끝에서 다가옴. 가까워지면 화면 가장자리에 서리가 끼고 바람 소리가 커지며 펭귄이 뒤를 돌아봄.
  4. 섬 끝: 큰 도약대 → 바다 위를 날아 다음 섬으로(카메라가 물러나되 펭귄이 잘 보이는 거리 유지, 다음 섬이 앞에서 다가오고 새 섬 이름이 뜸). 눈보라는 섬 입구에서 다시 뒤로 밀려남.
  5. 잡힘: 눈보라 정령이 펭귄을 눈덩이로 감싸 데굴데굴 → "오늘은 여기까지!" → 결과 화면.
  6. 결과: 거리·물고기·최고 기록·다음 섬까지 남은 거리·플레이 진단 한 줄 → [다시 날기] 가 가장 큰 버튼. 강화할 수 있으면 [강화] 버튼에 표시.

6. 콘텐츠: 섬(레벨) 구성

섬 하나 = 레벨 하나. 섬 끝 도약대에 닿으면 그 섬을 깬 것. 섬마다 새 요소를 하나씩 도입하고, 다음 섬에서 익힌 요소를 섞음.

  • 오늘의 섬: 날짜로 정해지는 특별 섬 + 하루 한 가지 조건(예: 얼음 많은 날). 하루 첫 완주 보상.
  • 끝없는 하늘: 9번 섬 이후 무작위 구간 조립으로 무한 진행(기록 경쟁용).

9. 아트 방향

  • 손으로 그린 동화책 같은 북극: 두껍고 부드러운 남보라색 외곽선, 채도 높은 그라데이션, 종이 결 질감, 빛 번짐. 캐릭터는 큰 눈과 말랑한 늘어남/찌그러짐.
  • 팔레트: 하늘 청록 → 복숭아빛 지평선, 눈은 흰색 + 라벤더 그림자, 펭귄 남색/크림/주황 부리, 빨간 목도리가 정체성.
  • 모든 스프라이트는 같은 SVG 리그에서 생성 → 어느 화면에서도 같은 펭귄.
  • UI도 같은 외곽선·질감·폰트. 이모지 사용 안 함.

10. 사운드 방향

  • 밝고 장난스러운 실로폰·플럭·패드 위주 배경음, 오래 들어도 거슬리지 않는 낮은 템포.
  • 효과음은 계층화: 물고기 연속 획득은 음계가 올라감, 완벽 착지는 종소리, 눈꽃 질주는 화음 확장.
  • 진동: 약(완벽 착지) / 중(눈꽃 질주, 새 기록) / 강(섬 도착, 잡힘). 설정에서 끔.

5. 의도적으로 하지 않은 것

  • 광고·인앱 결제·상점·유료 재화: 요구대로 넣지 않음.
  • 실제 로그인·클라우드 저장·분석 서버: 연결할 자리(src/services/services.js)만 만들고 실제 서비스는 붙이지 않음. 지금은 기기 안 저장(localStorage)과 콘솔 출력.
  • 네이티브 앱 묶음(APK/AAB/IPA): 만들지 않음. 스토어에 올리려면 웹뷰 래퍼(예: Capacitor, TWA)로 감싸는 단계가 더 필요합니다.
  • 생성형 영상 모델로 만든 컷: 이 환경에서 쓸 수 있는 영상 생성 모델이 없어 사용하지 않음. 대신 게임 렌더러로 카메라만 연출한 "시네마틱" 한 컷(23.2~25.5초, 슬로모션 클로즈업)을 넣었고, 나머지는 전부 실제 플레이 화면입니다. 게임에 없는 장면은 넣지 않았습니다.
  • 스토어 배지(Google Play/App Store 로고): 상표 사용 문제로 영상 끝 카드에 넣지 않고 "지금 바로 날아 보세요!" 문구만 넣음.
  • iOS 진동: iOS 사파리는 진동 API가 없어 진동이 나지 않음(설정에 안내 문구). 오류 없이 넘어가도록만 처리.
  • 그리드형 타일셋: 지형이 곡선(점 보간)이라 격자 타일셋을 쓰지 않음. 대신 눈 결 텍스처·지층 무늬를 지형에 입힘.

  • 펭귄이 화면에서 작은 편: 360px 폭 기준 미끄러질 때 약 45~70px. 속도·고도에 따라 카메라가 물러나며 더 작아짐. 앞을 내다보는 데는 유리하지만 실제 사람에게 작게 느껴지는지는 확인하지 못함.
  • 첫 섬이 쉬워짐: 시작 언덕을 늘린 뒤 초보 봇의 첫 섬 통과율이 88%. 첫 판에 새 섬 도착을 경험하게 하려는 의도지만, 너무 쉽다고 느낄 수 있음(사람 테스트 필요).
  • 영상의 손가락 위치: 화면 아래 88~96% 높이에 있어 TikTok·Reels처럼 아래쪽에 자체 문구를 겹치는 플랫폼에서는 가려질 수 있음. 플랫폼별 광고로 쓸 때는 손가락을 더 위에 두고 다시 렌더링하는 것이 좋음(src/app.js의 drawFinger, tools/trailer.mjs로 재생성 가능).
  • 영상 속 눈꽃 질주의 화면 효과(가장자리 빛)는 작은 화면에서는 잘 안 보임. 금색 "눈꽃 질주!" 글자로 전달.
  • 영어 화면에서 강화 카드의 "Lv.3"가 다음 줄로 넘어감(360px). 잘리지는 않음.
  • 저장은 기기 안(localStorage)만: 브라우저 데이터를 지우면 진행이 사라짐. 클라우드 저장은 자리만 있음.
  • 배포 빌드에도 window.__app이 노출됨: 혼자 하는 게임이라 기능 문제는 없지만, 서버 보상·순위가 생기면 막아야 함.
  • iOS 사파리: 진동 없음, 첫 탭 전에는 소리가 나지 않음(브라우저 정책).
  • Lighthouse 성능 점수는 헤드리스 기준(아래 4절). 텍스트 압축(gzip/brotli)은 서버 설정에 달려 있어 게임 쪽에서 해결할 수 없음.

7. 실제 기기에서 확인하지 못한 것

  • 실제 휴대폰(저사양 Android, iPhone)에서의 프레임·발열·배터리: 헤드리스 Chromium에서 CPU 제한으로만 측정. 헤드리스는 GPU 없이 그려서 실제 기기와 그리는 비용이 다릅니다.
  • 소리를 사람이 들어 본 것: 효과음·음악은 파형·스펙트럼·음량 통계로만 점검했고 사람이 듣고 평가하지 않았습니다. 반복 재생 이음새는 수치로만 확인.
  • 앱 전환 후 소리 복귀, 잠금 화면 후 복귀: 코드(visibilitychange → suspend/resume)만 있고 실제 기기로 확인하지 않음. iOS 사파리의 오디오 잠금 해제 동작도 미확인.
  • 진동의 실제 느낌: 패턴 6종을 코드로 나눴지만 실제 기기에서 세기를 느껴 보지 않음.
  • 노치·홈 바 안전 영역: CSS env(safe-area-inset-*)와 흉내 모드(디버그 패널)로만 확인.
  • 실제 사람의 첫 판 이해도, D1 리텐션: 봇과 시뮬레이터로 만든 추정입니다. 실제 사람 테스트가 필요합니다.
  • 글꼴 렌더링 차이: 게임 글꼴(Jua/Fredoka 일부 글자만 담은 내장 글꼴)은 Chromium에서만 확인.

3. 이탈 진단 기준 — "왜 안 돌아왔나"

첫날 마지막 run_end 몇 개와 세션 기록으로 이탈한 사람을 다음처럼 나눕니다. 한 사람이 여러 유형에 걸리면 위에 있는 것을 우선합니다.

  1. 조작을 못 알아챔 — 판 3개 이하, 마지막 판들에서 pressUp ≥ 45% 또는 releaseDown ≥ 50%, perfects 0~1. → 첫 판 안내/손가락 힌트, 결과 화면 팁(tip.pressUp, tip.releaseDown)이 실제로 보였는지(hint_shown) 확인.
  2. 같은 섬에서 막힘 — fails ≥ 3인 상태로 이탈, 같은 island에서 progress가 오르지 않음. → 도움 장치(run_start.assist > 0)가 켜졌는데도 이탈했다면 해당 섬 난이도·눈보라 속도를 낮출 후보. 섬별 실패 분포를 island로 나눠 확인.
  3. 물고기가 모자람(경제 벽) — 마지막 3판 동안 upgrade_purchase도 building_built도 없고, 남은 물고기 < 가장 싼 강화·건물 가격. → currency_earn{source:run} 판당 평균과 다음 가격 비교. 강화 비용 곡선/섬 보너스 조정 후보.
  4. 할 게 없다고 느낌(지루함) — 판 수 15 이상인데 마지막 5판에 level_reach{first:true}, newBest, 구매가 모두 없음. → 새 섬 간격, 섬 목표(goal_complete), 오늘의 할 일 완료율 확인.
  5. 기술 문제 — perf_sample.fps 중앙값 < 40, 또는 session_end.seconds < 20인데 run_start가 없음(첫 화면에서 떠남). → 기기·품질 설정별 fps, 로딩 시간.
  6. 분류 안 됨 — 위에 해당하지 않음. 플레이 시간이 충분하고 진행도 좋았던 사람(정상적인 이탈)으로 보고, 재방문 장치(출석 선물·건조대·알 부화) 노출 여부만 확인.

4. 재방문 장치가 작동하는지

  • 다음 날 들어온 사람 중 streak_claim 비율, 건조대 수거(currency_earn{source:rack}) 비율, 부화(egg_hatched)를 본 비율.
  • 둘째 날 첫 판까지 걸린 시간(session_start → run_start): 팝업이 판을 막지 않는지(목표: 중앙값 10초 이내).

5. 확인 방법(개발 중)

개발 빌드(out/dev/index.html)의 DEV 패널 → Analytics log에서 최근 이벤트와 값을 바로 볼 수 있습니다. 진행 속도 기대치는 node tools/run-sim.mjs 70 6(가상 플레이어 시뮬레이션)으로 다시 계산할 수 있습니다.
